# 规约模板与写法

规约陈述系统必须满足什么，不描述它如何实现。本文是给没写过规约的人的入门路径：先建立「什么算规约」的判断，再按六种形状各写一条，最后用反例自查。仓库里已有的规约实例在 [PLAN.md](../PLAN.md) 与 [scripts/patch-surface.sh](../scripts/patch-surface.sh)，本文不重复它们的条款。

## 先判断一段话算不算规约

一个判据：能据此写出机器可自动检查的断言，才叫规约；只能靠人读着点头，那是需求或背景。

「取款功能要正确」是需求。「任何时刻余额不低于零」是规约，因为它能变成 `assert(balance >= 0)`。这条判据决定了后面所有模板的写法——写不出检查方式的条目，不写进规约清单。

## 六种形状

按会出什么事来分，不按「前置／后置／不变式」这类形式化术语分。看到形状就知道该往哪想。

### 不变式

任何时刻都成立的条件，通常最该被保护的那条。

```
任何时候都成立：<条件>
它会被什么破坏：<并发／异常／超时／重启>
```

例：`任何时候都成立：余额 ≥ 0`；破坏方式：两笔取款并发读到同一余额，各自扣减。

### 契约

一次调用的双方各担什么责任。

```
调用 <入口> 前必须：<调用方责任>
调用后保证：<实现方责任>
违反前置条件时：<报错／未定义行为／防御性处理>
```

最后一行最常被漏掉，而它决定出问题后责任归谁，也决定调用方能否依赖前置条件而不做重复校验。

### 顺序

一条必须在另一条之前。

```
<A> 必须发生在 <B> 之前
顺序反了会怎样：<具体后果>
```

例：`必须先完成存储初始化再接受请求`，反了会写入未打开的数据库。

### 恰好一次与幂等

重复执行会怎样，重试时靠什么识别。

```
重复执行 <操作> N 次，效果等同于 <一次／N 次>
重试时如何识别已执行：<幂等键／状态位>
```

写下这条时往往发现代码里没有识别手段。分布式的重复扣款、「发了两遍」类事故都在这一格。

### 守恒与边界

总量不变，或有上下界。

```
总量守恒：<初值> − <当前值> = <所有成功操作的累加>
边界：<下界> ≤ <量> ≤ <上界>
```

对账类逻辑只靠这一条就能暴露大部分不一致。

### 失败原子性

多步操作中断时，已完成的部分留不留。

```
<多步操作> 中任一步失败时：<已完成部分回滚／整体不可见>
```

## 每条规约附一个反例

这是最有效的一条约束：**每条规约必须同时写出一个试图违反它的场景**。

```
规约：任意时刻余额 ≥ 0
反例尝试：两笔取款并发，各自读到余额 100，都扣 80 → 余额 −60，违反成立
```

写得出反例，说明知道这条在防什么；写不出反例，那条规约多半是空话。反例本身还能直接变成测试用例。

## 起步只写三条

逐条枚举会写成流水账，而且写不全。任何模块先只回答三个问题：

1. 最怕被破坏的那条不变式是什么；
2. 最容易被误用的入口，前置条件是什么；
3. 最怕发生的那件事，用人的话说出来。

写完这三条通常会冒出新的一条——模板的作用是逼出那个「原来这个也得考虑」，不是产出完整规约。

## 从已有事实里捞

从零想规约比从现有材料里捡慢得多。已有规约通常藏在这些地方：

- 代码注释里写着「这里必须先初始化」——一条顺序规约；
- 测试名写着 `rejects empty input`——一条前置条件；
- 线上事故复盘里的「什么本该拦住它」——一条不变式；
- 门禁脚本里的检查项——已经是可执行的规约，只是没这么称呼。

捞出来的条目贴近真实风险，也省掉了抽象边界的选择成本。

## 验收：由谁检查

| 层级 | 例子 | 谁来保证 |
| --- | --- | --- |
| 可执行规则 | 补丁首行必须有「变化理由：」 | [scripts/patch-surface.sh](../scripts/patch-surface.sh) 断言，不合规直接失败 |
| 代码契约 | 前置条件校验、不变式断言 | 运行时 `assert` 或类型系统 |
| 接口约束 | 打包产物的文件归属 | [PLAN.md](../PLAN.md) 的打包身份，配合验收脚本 |
| 文字规约 | 本文这类无法自动检查的条款 | 评审 |

前两行能在无人值守时拦住破坏。写在第四行的东西会腐烂——没有人读就会和现实脱钩，所以要经常问一句：这条能不能降到上一行。

## 一个常见误区

规约写漏时，验证仍然会通过。若栈的规约只写「`pop` 后长度减一」和「返回值是之前压入过的元素」，一个队列实现完全满足它，任何验证器都会判通过。

验证器只保证写下的性质，不保证没想到的性质。所以难的是知道该证明什么，而不是证明本身。
