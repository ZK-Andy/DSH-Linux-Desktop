# AGENTS.md — 文档标准

本文件规定文档结构、Markdown 层级、写作规则与 `verify-doc-budgets` 的字数上限。放置与校验用 [dsh-doc](../.agents/skills/dsh-doc/SKILL.md)，篇幅判断与编辑取舍用 [dsh-prose-standard](../.agents/skills/dsh-prose-standard/SKILL.md)。

## 文档结构

本节规则只管人读文档；[Agent Note](../.agents/notes/README.md) 另有一套格式，不受本节约束。文档的主题与树中位置决定它的范围：写清自己的主题，只在必要时按用途、职责与高层行为提及直接子项，更低层的细节链接到拥有它的下级。文档类型不放宽这条范围：例如一份调研报告可以对自己的主题写尽，但不能顺带成为更新链的规格。测试机制、夹具与脚本属于最低的拥有层级，上层只链接。

每份范围内的文档，先判定它是教程还是参考。教程沿一条有序路径到达某个结果，只引入当步需要的概念；参考界定一个查阅范围与当前行为，不设教学顺序。教程与参考都成篇幅时分开写；其中一部分很小时用章节标签标明。

写教程前，先私下判定读者的起点知识与每个概念的难度（入门、中级、高级）。前置概念先于依赖它的概念，难度逐步上升，用不上的高阶内容挪到后面的教程或参考。

按此顺序落笔：在树中定位文档；确定它允许的细节层级；选择教程或参考；若是教程，按前置关系与难度排序概念；把属于下级的细节迁走；把对低层的解释换成指向其拥有者的链接。

## 层级分类：一个事实只有一个归属

每个事实只有一个归属——职责落在哪一层就写在哪层，别处链接过来。

| 层级 | 职责 | 不放这里 |
|---|---|---|
| 根 `AGENTS.md` | 常驻指令：每次会话都需要进上下文的规则，一条一到三行，后附其归属的链接 | 故事、范例、特定情境的流程、任何与所链归属重复的转述 |
| 子树 `AGENTS.md`（`docs/`、`.agents/notes/`、`scripts/`、`.github/`） | 只对该子树成立的指令 | 根文件已载的仓库级规则 |
| [architecture.md](architecture.md) | 有序的全局图：仓库构成、补丁分层、模块边界、接缝与扩展点；改 `patches/` 之前先读 | 类型与字段定义（→ 各模块文档）、逐补丁实现细节（→ 补丁首行与 Agent Note）、决策理由（→ Agent Notes）、实现状态标注 |
| [PLAN.md](../PLAN.md) | 已交付的产品契约：需求 R1–R5、打包身份与安装布局、更新语义与退出码、里程碑、明确不做、已知约束，以及待迁移登记表——`scripts/patch-surface.sh` 解析它作为唯一豁免源 | 决策的取舍过程（→ Agent Notes）、构建输出的逐步说明（→ architecture.md）、工具用法（→ development.md） |
| [Agent Notes](../.agents/notes/README.md) | 现行决策记录：为什么这么定、放弃了什么、必须验证什么；`implemented/` 用现在时描述已交付的现实 | 迁移计划、验收清单、夹具走查，以及决策已落地后的假设式表述（"应该……"）；`archived/` 是冻结历史，永不是现行权威 |
| [development.md](development.md) | 贡献者环境、日常流程、CI 概要 | 运行时与版本取舍（→ Agent Notes）、会与 `package.json` 脚本漂移的逐条检查清单 |
| `docs/` 下的专项参考（[frameless-alignment.md](frameless-alignment.md)、[linux-packaging-survey.md](linux-packaging-survey.md)） | 单一主题的参考或调研：对齐项清单、候选方案对比与实测数据 | 仓库级规则、其他主题的结论、决策记录 |
| 技能（`.agents/skills/`） | 可复用的工作流与专项判断标准 | 产品契约与运行时契约（→ 文档或源码） |
| [README.md](../README.md) | 面向使用者：这是什么、怎么装、怎么更新、前置条件 | 内部构建细节、决策理由、贡献者流程 |
| [CONTRIBUTING.md](../CONTRIBUTING.md) | 提交契约：分支、PR 描述、合并前的本地检查 | 逐条门禁实现（→ `scripts/`）、产品规格 |

放置一句话：缺陷复盘 → Agent Note 或专项参考；理由 → Agent Note；步骤 → development.md 或对应参考；契约 → PLAN.md；常驻规则 → 根 `AGENTS.md` 并附理由链接；使用者须知 → README.md。

## 写作规则

- **写当前状态。** 历史留在提交、PR 与 Agent Note 里。正文只讲现行机制，不写"曾经""后来改成"。会话编号、日期戳、`[x]`/`[ ]` 进度标记不进入文档正文；进度由提交与其后的文档状态表达。
- **一段一个物理行**（`verify-md-wrap`）：靠编辑器软换行，不要在段中敲回车。代码块、表格、列表结构保持原有格式。
- **`ts` 代码块必须能编译**：本仓库目前不含可执行 TypeScript 文档示例，新增之前先建立 `doc-typecheck` 并在此登记机制，否则不要写带类型的示例块。
- **同一个改动内更新它的归属**：某机制改了，描述它的那份文档在同一次提交里改；不要追加变更记录。
- **注释与 JSDoc 写完整契约，不写推理过程。** 保留行为、失败、时机、归属、例外与后果，删掉叙述性旁白、测试走查、评审分析与代码转述。本地的契约留在本地，理由链接出去。
- 直接写：点名执行者与事实（详见 [dsh-prose-standard](../.agents/skills/dsh-prose-standard/SKILL.md)）。不要用比喻代替具体的检查、类型、API、操作或行为。

## 字数预算

[scripts/doc-budgets.manifest.json](../scripts/doc-budgets.manifest.json) 登记常驻文档的上限，`pnpm run verify-doc-budgets` 拒绝超限与文件缺失。

计数口径因为本仓库文档是中文而不同于上游的 `wc -w`：一个汉字（含日文假名、韩文谚文）记一个词，其余文本按空白切分为词，两者相加。纯英文文档下这与 `wc -w` 等价。

门禁变红时按此顺序处理：

1. **迁走**属于别层的内容，留一行链接。
2. **压缩**确实属于本层但可以更短的内容。
3. 只有字数确需这个空间时才**提高**上限，并在 PR 里说明 manifest 的这处改动。上限定低是预算本身的问题。

上限是护栏，不是削减目标。处在上限或以下时留至少 5% 余量；高于上限时冻结上限，直到迁走或压缩把文档带回上限以下；只有文档还有余量时才下调。

当前上限：根 `AGENTS.md` 1850；`PLAN.md` 5410；`README.md` 640；`CONTRIBUTING.md` 320；`docs/AGENTS.md`（本文件）2380；`docs/architecture.md` 1090；`docs/development.md` 790。未登记上限的层级——子树 `AGENTS.md`、`.agents/notes/README.md`、`docs/` 下的专项参考——靠评审管。

## 废话清单

任何文档都要按这份清单自查；[dsh-doc](../.agents/skills/dsh-doc/SKILL.md) 把它当作审计清单跑：

- 重复的规则：搜一句独特措辞，只留一个归属，其余改成链接。
- 不在其允许层级的历史：写当前事实，历史链接到它的归属。
- 正文或图里的实现状态标注（"已实现！""未来：……"）。状态会腐烂，仓库布局与包清单才是它的载体。
- 手抄的目录、清单、JSDoc 或测试与包的状态——源码或生成器才是权威时一概不抄。
- 推理过程：逐步实现叙述、显而易见分支的证明、测试走查、被否掉的局部备选。留下最终契约或持久理由，删掉推导路径。
- 在相邻方法旁重复理由，而不是在拥有该能力的那一处写一次。
- 段落墙：一段话塞进多条规则与括号补充。拆开，或把细节降级到它的归属。
- 强调膨胀：到处都是加粗、全大写、"关键的是"，等于什么都不突出。强调只留给改变行为的那一句。
- `implemented/` Agent Note 里的假设式表述："应该"、迁移计划、验收清单。已实现的 note 描述现实，规范见 [implemented 说明](../.agents/notes/implemented/AGENTS.md)。
