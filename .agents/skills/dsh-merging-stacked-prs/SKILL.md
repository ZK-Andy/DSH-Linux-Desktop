# 合并堆叠的 PR

本仓库的改动经常是串起来的：先改门禁脚本，再改仓库文档，最后改 CI。后一个在前一个合并前无法独立通过门禁，因此不能并行落地。

## 顺序

从栈底往上，一次只合一个。合完立刻把下游分支 rebase 到 `main`——不要 merge `main` 进去，那会让 diff 里出现别人的提交。

每个 PR 合入前单独确认：它的门禁在**它自己的 base 上**是绿的。栈底绿而栈中红，说明问题在栈中那一层，不要往后看。

## 冲突

门禁脚本与文档的冲突多为同一行的文本差异，重放即可。**补丁文件的冲突不要手工编辑**：补丁由 `scripts/regen-patch.sh` 生成，手改出来的 patch 与生成器下一次输出不一致，`patch-surface.sh` 查不出来但重放会坏。冲突时回到 `upstream/` 工作树，按新的 base 重放，再重新生成。

## 合完之后

`main` 上的 `patch-gate.yml` 不会因为合并而重跑——它只在 `pull_request` 上跑。合并后如果上游 tag 变了，需要单独一次「跟随上游重放补丁」的改动，那是一个新的 PR，不是这个栈的延续。
