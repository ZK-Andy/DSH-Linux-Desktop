# 错误处理

## 静默是最坏的

失败要么改变控制流，要么留下一条能定位的日志。两者都没有的 `catch {}` 是在制造将来的悬案。

## 在边界翻译

外部系统的错误码在边缘翻译成我们的概念，不往上抛原始形态。dnf 的退出码在 `dsh-update-helper` 里翻译成 64（参数非法）/77（非 root）/70（公钥导入失败）；`rpmsign` 的失败在 CI 步骤里翻译成带原始输出的 `::error::`。上层只看见我们的概念。

## 不要兜底成空值

查不到版本时不要当成「已是最新」，解析不到渠道时不要当成 stable。要么明确报错，要么明确降级并在日志里写清「渠道可能不生效」——降级是一种有意的行为，必须写在代码里，不能是 `|| default` 的副作用。

## 让失败自己说话

门禁脚本失败时打印违规的文件:行号与原始文本，不打印「检查失败」。CI 步骤失败时贴原始 stderr，不转述。

## 幂等

`%post`、`%postun`、helper、`apply-patches.sh` 都会被执行不止一次。写之前问：第二次跑会发生什么？

## 报错文案写给谁

写给下一个读日志的人。他不知道你的上下文，所以文案里要有：什么失败了、在哪、为什么、怎么改。例：`docs/AGENTS.md:45  ../scripts/doc-budgets.manifest.json  (target does not exist)` 比 `link check failed` 有用得多。
