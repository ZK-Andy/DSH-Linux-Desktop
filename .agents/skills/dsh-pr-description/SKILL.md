# PR 描述

读者是三个月后的自己和一个没参与讨论的人。他需要的不是改动清单——diff 里有——而是「为什么要动」和「怎么验证」。

## 结构

**一句话说清改了什么。** 标题里放动词与对象，不放「若干修复」。

**为什么。** 一段。指向触发这次改动的具体事实：哪个门禁红了、哪条上游行为变了、哪个用户路径断了。没有这一段，读者无法判断改动是否解决了问题。

**怎么改的。** 只在方案不显然时写。说了「用静态断言守住补丁形状」就不必再列断言了哪几条——`patch-surface.sh` 里有。

**怎么验证的。** 写清验证环境：容器、真机、还是只有静态断言。**容器通过不等于真机通过**，这一条必须写明，不能含糊成「已测试」。

## 补丁类改动的必备项

改补丁时，描述里要有 [`AGENTS.md`](../../../AGENTS.md) 要求的四项：改了哪个补丁、碰了哪些上游文件且每处是挂钩还是实现、`main.ts` 净增行数、是否产生了重复的事实或组件。

## 不要

不要贴粘贴的日志。摘要成一行结论，需要细节的人会去翻 CI。不要写「详细改动见 diff」——那不是省事，那是把解释的责任推给读者。不要用「优化」「重构」「完善」这类词，它们不描述任何可验证的变化。
